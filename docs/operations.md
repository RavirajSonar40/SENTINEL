# Sentinel — Production Operations Guide

## Monitoring

### Health Endpoints

| Endpoint | Purpose | Auth | Check |
|----------|---------|------|-------|
| `GET /health` | Liveness — process is running | No | Always 200 if up |
| `GET /health/ready` | Readiness — dependencies reachable | No | Postgres, Qdrant, Redis |
| `GET /health/db` | Database connectivity | No | `SELECT 1` |
| `GET /system/health` | Full infrastructure check | Yes | Postgres, Qdrant, Redis, LLM |

### What to Monitor

1. **Render Dashboard**: CPU, memory, request count, response times
2. **`/health/ready`**: Returns `{"status": "ready"|"degraded", "checks": {...}}` — alert on `degraded`
3. **`/system/health`**: Returns per-dependency status — alert on any `error`
4. **GitHub Actions keep-alive**: Pings `/health` every 10 min to prevent Render free-tier sleep

### Key Metrics (in-memory, reset on restart)

- Request count, error rate
- LLM calls and estimated cost
- Active investigations, evidence count
- Task queue depth (Redis-backed tasks persist across restarts)

### Logs

- Structured logging via Python `logging` module
- Log level controlled by `LOG_LEVEL` env var (default: `INFO`)
- Key loggers: `sentinel.startup`, `sentinel.approvals`, `sentinel.remediation`, `sentinel.investigation`

## Rollback Procedures

### Backend Rollback (Render)

1. Go to Render Dashboard → sentinel-api → Deploys
2. Find the last known good deploy
3. Click "Manual Deploy" → "Deploy previous commit"
4. Render rebuilds and restarts with the previous code
5. Alembic migrations are backward-compatible — no rollback needed for DB

### Database Rollback

- All migrations are in `backend/alembic/versions/`
- Migrations 018-021 are additive (new columns, sequences, constraints)
- To rollback a migration: `alembic downgrade -1` (run in Render shell or locally)
- **Never drop columns** — they may be referenced by running code

### Frontend Rollback (Vercel)

1. Go to Vercel Dashboard → SENTINEL → Deployments
2. Find the last known good deployment
3. Click "..." → "Promote to Production"
4. Instant rollback — no rebuild needed

### Worker Rollback (Render)

1. Same as backend — Render Dashboard → sentinel-worker → Deploys
2. Click "Manual Deploy" → "Deploy previous commit"
3. Worker shares the same codebase as the API

### Infrastructure Rollback

- **Postgres**: Render-managed, automatic backups (point-in-time recovery available on paid plans)
- **Qdrant**: Data is indexed, can be rebuilt from source. Delete collection and re-index if corrupted.
- **Redis**: Ephemeral cache/queue. Loss is non-critical — tasks retry, rate limits reset.

## Incident Response for Sentinel Itself

If Sentinel goes down:

1. Check `/health/ready` — identify which dependency is failing
2. If Postgres is down: Render auto-reconnects. Check Render dashboard.
3. If Qdrant is down: Investigations still work (graceful degradation). Re-index after recovery.
4. If Redis is down: Task queue falls back to in-memory. Tasks in progress are lost.
5. If LLM is down: Chatbot and investigation use mock responses. No data loss.

## Security Checklist

- [ ] `SECRET_KEY` is auto-generated by Render (not hardcoded)
- [ ] `DATABASE_URL` is set in Render dashboard (not in code)
- [ ] GitHub tokens encrypted at rest in `GitHubInstallation.tokens_encrypted`
- [ ] Webhook HMAC verification enabled via `GITHUB_WEBHOOK_SECRET`
- [ ] Rate limiting: 200/min global, 10/min login, 5/min register
- [ ] CORS restricted to Vercel origins + configured `CORS_ORIGINS`
- [ ] Non-root Docker user (`sentinel`)
- [ ] No autonomous merge — all PRs require human approval
